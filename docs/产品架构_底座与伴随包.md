# 产品架构：云 OS 底座 + 棋牌伴随包（用户 2026-09-16 补充背景）

> 这一层是**产品形态**的定调，直接影响"记牌/AI 托管"要做到哪一步、数据往哪走、钱从哪扣。

## 两个交付物

### 1. 主应用：云 OS 底座（上架 MM，独立商品）

| 项 | 内容 |
|---|---|
| 形态 | **MM 上可独立下载的主商品** |
| 职责 | 用户登录 / **Token 资产账户** / Token 扣费与充值 / 云实例创建销毁 / 窗口管理 / 应用生命周期调度 / 云资源编排 / **统一埋点计费** |
| 资金 | 所有 Token 交易、余额、订单**全部在底座** |
| 计费主体 | **底座**（不是棋牌游戏）|

### 2. 伴随应用：棋牌业务包（完整业务 APK）

| 项 | 内容 |
|---|---|
| 内容 | 斗地主 / 掼蛋 + **AI 记牌** + **自动托管** |
| 分发 | 随底座分发；**无独立 MM 货架、不能单独下载**；由底座拉起、底座控制启停；**卸载底座则一并卸载** |
| 职责 | 对局 UI / 房间 / **牌局逻辑** → 通过 **IPC 把牌局状态传给内部 AI 模块** → 接收 AI 出牌指令执行出牌 |
| 计费 | **AI 算力消耗由伴随应用上报到底座** → 底座扣减用户 Token |

## 对当前开发的三条影响

| # | 影响 | 落地 |
|---|---|---|
| ① | **记牌/托管是棋牌包内功能**（不是外挂）| 记牌器保持为可被包内 AI 模块直接调用的独立模块 ✓ |
| ② | 牌局状态两条通路：**自研包走 IPC** / **第三方闭源游戏走纯视觉** | `GameLog` + `CardTracker` 设计成**输入无关** ✓；两条喂入适配器（IPC 适配器待做）|
| ③ | **AI 算力必须计量上报**（底座扣费）| 已加 `platform/usage.py`：只记消耗、不带价格（定价在底座）✓ |

## 计量口径（`platform/usage.py`）

| kind | 含义 | 打点位置 |
|---|---|---|
| `vlm_read` | 视觉读牌调用（次）| 适配器每次读手牌 / 读桌面 |
| `rl_infer` | RL 决策推理（次）| `_decide_rl()` |
| `decide` | 决策（次）| `decide()` |
| `proxy_minute` | 托管时长（分钟）| 托管循环按分钟 |
| `vision_frame` | 视觉处理帧（帧）| 备用 |

- 落盘：**`data/usage.db`（sqlite，表 usage）**（2026-09-21 起：数据一律走 sql，json/csv 已删）
- 上报：`GET /usage/batch` 取批次 → 底座确认 → `POST /usage/ack`（**幂等**，重发不重复扣费）
- 查询：`GET /usage`（汇总：按 kind / 未上报数）、`GET /usage/events`

## 待与底座对齐的口径（产品决策，非技术）

2. 上报频率与断网重传策略
3. `user_id` / `device_id` / `game_id` 的命名与归属（底座下发）
